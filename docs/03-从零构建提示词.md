# 03 · 从零构建提示词（给 AI Agent 的施工蓝图）

> 用途：把下面**整段提示词**粘贴给一个有本机终端权限的 AI Agent（DSH / Codex / Claude Code 等），即可从零复刻本功能。
> 前置：Agent 需要能在 Windows 上装/改文件、跑 Node 脚本；首次执行前请自行替换所有 `<...>` 占位。

## 使用说明

1. 确认本机有 QQ NT、Node.js 22+、DSH（或可替代的模型后端）；
2. 替换提示词末尾「本机参数」表中的占位；
3. 粘贴整段，要求 Agent **按阶段实施并逐阶段验收**，不要一次性写完就交付；
4. 全部完成后按「验收清单」逐条跑命令验证。

---

## 提示词正文（复制以下全部）

```text
你是 Windows 上的高级全栈/自动化工程师。请在本机从零实现一套「QQ ↔ DeepSeek(DSH) 双向对话」系统，交付可长期运行的代码 + 文档。严格分阶段实施：每个阶段先写实现、再跑该阶段的验收命令、把结果贴出来；验收失败先修再进入下一阶段。

# 一、最终目标（验收即定义）
我的手机/电脑 QQ 用主号，给小号发私聊消息（不需要任何前缀），小号背后的 NapCat 把消息推给本地桥，桥投递给 DSH 会话，DeepSeek 的回复自动发回 QQ 给我。要求：
1) 私聊免前缀：白名单 allowFrom 内的号码，发任何内容都直达模型；
2) 消息串行处理（不并发抢写同一会话），有去重（同一条只处理一次）；
3) 回复发回 QQ，单条上限 1200 字符（超出截断并注明）；
4) 会话自动轮换：满 N 条 / N 小时 / 上下文压力 N token / 本段估值 ¥N 任一命中即换新会话，并把上一段摘要注入下一条消息（零额外模型调用）；
5) 余额闸：余额 ≤ ¥30 时直接回一句提示、不调用模型；充值后自动恢复；
6) 桥空闲时零模型调用、零费用；日志可追溯（收/投/回/轮换/余额）；
7) 所有 token、QQ 号、会话 id 只存本机，不入 git。

# 二、环境与前提（先检查，缺什么先装/说明）
- Windows 10/11 x64；
- QQ NT 客户端（独立副本用于小号，不能与主号共用同一客户端实例）；
- NapCat（OneBot 11 实现，官方发行版），可注入/独立客户端启动；
- Node.js 22+（桥只用内置模块：node:http、fetch、node:fs、child_process）；
- DSH 桌面版 + session-hub（本机 HTTP 服务）；或替换为任意 OpenAI 兼容 HTTP 后端（见「可替代后端」）。
- 端口约定（都在 127.0.0.1）：
  * 3000  NapCat HTTP 服务端（桥调它发消息）
  * 19390 桥的回调服务（NapCat HTTP 客户端推事件到 /onebot）
  * 6099  NapCat WebUI（可选，扫码/日志）
  * 19391 本项目的二维码登录页（可选）
  * DSH hub 端口不固定，读 ~/.dsh/session-hub.json

# 三、架构（照此实现，不要多引入框架/数据库）
你的QQ主号 --私聊--> 小号QQ(NapCat注入) --HTTP客户端 POST--> 桥(:19390/onebot)
桥 --HTTP POST--> NapCat API(:3000/send_private_msg) --发送--> 你的QQ主号
桥 --HTTP--> DSH session-hub /x-hub（GET /sessions、GET /sessions/{id}/tail、POST /sessions/{id}/send {text,mode:"queue"}）
桥 --读本地--> ~/.dsh/storages/session_projcache/sessions/<id>.json（token/上下文压力，仅读）
桥 --读本地--> ~/.dsh/session-hub.json（endpoint+token）、~/.dsh/balance-widget.json（余额端点 token）

# 四、实施阶段（每阶段有验收命令，必须通过）
## 阶段 0：环境探明
- 确认 node --version ≥ 22、QQ 进程、NapCat 可启动、DSH hub 可达；
- 读取 ~/.dsh/session-hub.json 拿到 endpoint/token，GET {endpoint}/sessions 应 200；
- 验收：把以上四项结果列表输出（版本/进程/hub 状态/端口）。

## 阶段 1：NapCat 登录与网络配置
- 启动 NapCat（独立 QQ 副本），扫码登录小号（提供二维码页或 WebUI 方式）；
- 写一份配置补丁脚本，向 NapCat 的 onebot11_<小号QQ>.json 中写入：
  * httpServers: 127.0.0.1:3000, messagePostFormat:"array", token=<随机32位>
  * httpClients: http://127.0.0.1:19390/onebot, messagePostFormat:"array", reportSelfMessage:false, token 同上
- 验收：用 OneBot API 调 get_login_info 返回小号昵称/QQ；用 send_private_msg 给主号发一条「桥自检」，主号能收到。

## 阶段 2：桥（核心）
实现 qq-bot-bridge.mjs，纯 Node 内置模块，要求：
- 配置加载：默认值 + 同目录 bot-bridge.config.json 深合并；
- 回调服务：POST {config.callback.path}，立即回 204（先 ack 再处理），校验 post_type==="message"；按 message_id:time:user_id 去重，seen 集合上限 5000；
- 触发判定：群聊默认不进（groups=false 直接忽略）；allowFrom 非空时必须命中；mode==="all" 直接放行，mode==="keyword" 需文本包含关键词（取关键词后剩余文本作 prompt，空则用全文）；
- 余额闸：读 ~/.dsh/balance-widget.json 的 token，请求 {endpoint}/x-balance，取 CNY 钱包余额；缓存 checkSeconds；≤ floorYuan 时回一句并 return（不调模型）；
- 会话：读 out/bot-session.json 的 sessionId；无则 POST /x-hub/sessions?cwd=<工作区> 建会话并落盘；若配置直接给了 session-xxx 则用它；
- 轮换检查（发送前）：读 out/bot-state.json 的 messages/since + projcache 的 pressureTokens/成本；任一触发则 spawnSync(rotate 脚本 --apply --json --reason ...)；成功则切新会话，失败 fail-open 继续用旧会话；
- 交接注入：若 out/bot-pending-handoff.json 存在，把 summary 前缀进 prompt 后删除；
- 投递：POST /x-hub/sessions/{id}/send，body {text, mode:"queue"}；prompt 模板=[来自 QQ 的对话 · <私聊/群> · 对方 QQ <id>]\n<正文>\n\n（这是 QQ 对话，请直接给出可以回复给对方的中文回答，不要带内部思考过程。）
- 等回复：每 2 秒 GET /x-hub/sessions/{id}/tail?n=30，取 time >= startedAt-2000 的最后一条 assistant 文本；超时 replyTimeoutMs 后放弃；
- 回发：POST OneBot send_private_msg（群聊则 send_group_msg），内容按 maxChars 截断；
- 串行：所有消息进入单一 Promise 队列，处理完一条再下一条；异常只记日志不崩；
- 日志：时间 ISO + 事件行，同时写 config.logFile（追加）；
- CLI：--check 输出 onebot/hub/session 三项自检 JSON；--dry-run 不发 QQ；--config 指定配置；--once 测试用。
- 验收：--check 三项 ok；--dry-run 下用一条模拟 OneBot 事件 POST 到回调，日志出现 [QQ]→[DSH]→[DSH→QQ] 且不真发 QQ。

## 阶段 3：轮换脚本（零 token）
实现 qq-bot-rotate.mjs：
1) 从 out/bot-session.json（或 --session）取旧会话；拒绝轮换 running 会话（除非 --force）；
2) 读 projcache：tokenUsage.totals、sessionStats、contextPressure、最近 10 轮对话摘要（prompt/response 各截 240/400 字）；
3) 生成交接件 markdown（≤4KB）写到 outDir/<YYYYMMDDHHmm>-<标题>-<id>.md，并追加索引文件一行；
4) --apply：POST /x-hub/sessions 建新会话（cwd 默认 rotation.cwd），hub 改名：新会话 → "QQ 对话 · 日常 · MMDD-HHmm"，旧会话 → "【已轮换 YYYYMMDDHHmm】<旧标题>"；
5) 写 out/bot-session.json（新 id）与 out/bot-pending-handoff.json（{summary, handoffPath, newSessionId}）；给桥返回单行 JSON {ok,oldSessionId,newSessionId,handoffPath,...}；
6) dry-run（默认）只打印计划+交接件预览，不写任何文件、不建会话。
- 验收：dry-run 输出计划；--apply 后 bot-session.json 指向新会话、交接件存在、旧会话已改名；桥下一条消息日志出现 [交接] 已注入。

## 阶段 4：可观测与护栏
- 余额闸阈值回信（§二.5）；
- 轮换 4 阈值全部可配；
- 日志轮转建议（按天/按大小，自行实现或文档说明）；
- 验收：把 balance.floorYuan 临时设成 9999 发一条消息 → 应直接回停机提示且不产生 DSH 回合；改回后恢复。

## 阶段 5：打包与文档
- 输出 GitHub-ready 目录：README（架构图/快速开始/配置表/安全边界/已知限制）、config/*.example.json、src/、scripts/、docs/（文档索引、现状清单、token 核算、本提示词、功能详解、运维手册、文件哈希）；
- .gitignore 排除：config/bot-bridge.json、out/、*.log、*.sqlite、*.db、.env；
- 所有 QQ 号/token/会话 id 用 <MAIN_QQ>/<BOT_QQ>/REPLACE_WITH_RANDOM_TOKEN 占位；
- 验收：README 按步骤在一台新机器（或从文档逐条走查）能完成部署；git 仓库内 grep 不到真实 QQ 号/token（自行扫描一遍并贴结果）。

# 五、可替代后端（没有 DSH 时）
若没有 DSH，把「投递/等回复」替换为任意 OpenAI 兼容 API：POST {base}/v1/chat/completions，Bearer key 从环境变量读取；保留「会话轮换」逻辑（用本地消息历史数组 + 摘要即可），其余结构与端口不变。

# 六、安全与隐私硬规则（必须遵守）
- 不做群发、不加好友、不主动私聊陌生人；只处理 allowFrom 白名单；
- 不读取/解密 QQ 数据库、不访问 QQ 进程内存、不绕过风控；
- 所有凭据只在本地文件/环境变量；提交前扫描仓库无真实 QQ 号/token/会话 id；
- 遵守 QQ 与 NapCat 的使用条款，账号风险由使用者承担；
- 日志不打印完整 token、完整 access_token、完整 cookie；QQ 内容属私人数据，只落本机。

# 七、成本纪律
- 桥空闲不得调用模型；每条 QQ 消息最多一次模型回合（注入摘要不额外调模型）；
- 轮换默认：120 条 / 24 小时 / 上下文 150000 token / 本段 ¥2.5；
- 余额 ≤ ¥30 自动停机；不做自动充值、不建额外定时器/自动化；
- 估算成本公式：(未命中输入×0.15 + 缓存读×0.003 + 输出×0.6)/1e6×7.2（人民币估算，非官方账单）。

# 八、实测坑（必须规避/写进文档）
1) NapCat 重启不保留登录态 → 需重新扫码；桥不用重启，重连后事件照常推送；
2) DSH hub 端口/token 会变：桥在启动时读取 session-hub.json，若 DSH 宿主重启，必须重启桥；
3) OneBot httpServers 与 httpClients 的 token 必须一致，否则 401/静默无事件；
4) 不要同时登录同一小号的普通 QQ 客户端与 NapCat 副本（互踢）；
5) QQ 事件 message 是 array 格式时，文本要遍历 segments 提取 text/at，图片等只留占位；
6) 回调必须先回 204 再处理，否则 OneBot 侧超时/重推导致重复；
7) UI Automation 方案（读屏）在提权 QQ 窗口下不可用；这只是兜底方案，主链路走 OneBot；
8) 不要打印完整 QQ 号/token 到日志或聊天记录，避免二次泄漏。

# 九、最终验收清单（逐条跑并贴证据）
[ ] node --version ≥ 22；[ ] get_login_info 返回小号；
[ ] 主号私聊小号发「在吗」→ 桥日志 [QQ]→[DSH]→[DSH→QQ]，QQ 收到回复；
[ ] --check 三项 ok；
[ ] 同一 message_id 重复推送只处理一次（日志只有一条）；
[ ] allowFrom 之外的号发消息被忽略（日志 [忽略]）；
[ ] 把 everyMessages 设为 1 → 下一条消息触发轮换，新会话生效、交接摘要注入；
[ ] floorYuan 设为 9999 → 直接回停机提示、无模型回合；
[ ] git 仓库 grep 真实 QQ 号/token 为空；
[ ] README 新机器部署步骤可执行。

# 十、本机参数（执行前替换）
MAIN_QQ=<你的主号 QQ>
BOT_QQ=<小号 QQ>
WORKSPACE=<新会话工作区，如 D:\AI\日常>
REPO=<仓库目录，如 D:\AI\DSH\dsh-qq-chat>
DSH_HUB=<endpoint，读 ~/.dsh/session-hub.json>
BALANCE_ENDPOINT=<http://127.0.0.1:<port>/x-balance>

开始执行：先输出「阶段 0 结果」，等我确认后再进入阶段 1（或按我指定的阶段推进）。
```

## 附：提示词设计说明（为什么这样写）

| 设计 | 原因 |
|---|---|
| 分阶段 + 每阶段验收 | 避免「一次写完、跑不起来」；每步都能失败、可判据 |
| 端口/目录/字段全部写死约定 | 桥和 NapCat 的对接细节最易出错（token 不一致、callback 路径） |
| 把「先 204 后处理」「串行队列」「去重」写进要求 | 这是 OneBot 接入最常见的重复回复/并发抢写根因 |
| 轮换与余额闸作为硬要求 | 控制成本是本项目的核心工程目标，不是附加项 |
| 安全红线单列 | 避免产出「群发/解密数据库」这类不可接受实现 |
| 实测坑清单 | 这些是本机踩过的真实问题，能省掉一轮轮返工 |
