# 04 · 功能详解（DSH QQ Chat Bridge）

> 一句话：**把 QQ 私聊当 DeepSeek 的聊天窗口**——消息经 NapCat/OneBot 进本地桥，桥投给 DSH 会话，回复原路发回 QQ；并在本地做会话轮换、交接摘要、余额闸与审计日志。

## 1. 它解决什么问题

- 手机上想用 DeepSeek，但不想开电脑/切 App → QQ 私聊小号即可；
- 想让它跑在**自己的工作区**（人格、记忆、工具、权限都属于 `D:\AI\日常`），而不是网页版；
- 长会话越聊越贵 → 自动轮换 + 交接摘要，成本可控；
- 不想账号/数据进第三方 → 全链路本机回环（NapCat ↔ 桥 ↔ DSH）。

## 2. 架构与端口

```
 你的QQ(主号) ──私聊──► 小号QQ(NapCat 注入的官方客户端)
        ▲                    │ OneBot 11 事件 → httpClients
        │                    ▼
        │            POST http://127.0.0.1:19390/onebot
        │                    │
        │            ┌───────────────────────┐    读文件     ┌────────────────────────────┐
        │            │  qq-bot-bridge.mjs   │◄─────────────│ ~/.dsh/session-hub.json     │
        │            │  · 去重/串行队列      │              │ ~/.dsh/session_projcache/…  │
        │            │  · 触发/余额/轮换     │              │ ~/.dsh/balance-widget.json  │
        │            └──────┬───────────────┘              └────────────────────────────┘
        │                   │ POST /x-hub/sessions/{id}/send {text,mode:"queue"}
        │                   ▼
        │            ┌───────────────────────┐
        │            │ DSH 会话（DeepSeek）  │── assistant 回复写回会话
        │            └───────────────────────┘
        │                   │
        └── send_private_msg（POST 127.0.0.1:3000）◄── 桥轮询 /sessions/{id}/tail 拿回复
```

| 组件 | 地址 | 说明 |
|---|---|---|
| NapCat HTTP 服务端 | `127.0.0.1:3000` | 桥调用 `send_private_msg` / `get_login_info` |
| 桥回调服务 | `127.0.0.1:19390/onebot` | 接收 NapCat 推送的消息事件 |
| NapCat WebUI/二维码页 | `127.0.0.1:6099` / `127.0.0.1:19391` | 扫码登录、状态查看（可选） |
| DSH session-hub | 端口不固定 | 读 `~/.dsh/session-hub.json` 的 `endpoint` + `token` |
| 余额端点 | `…/x-balance` | 读 `~/.dsh/balance-widget.json` 的 token |

## 4. 一条消息的完整生命周期

1. **主号私聊小号**，QQ NT 客户端渲染消息；NapCat 以 OneBot 事件 POST 到桥回调；
2. 桥**立即回 204**（先 ack，避免 NapCat 重推），解析 `post_type === "message"`；
3. **去重**：key = `message_id:time:user_id`，`seenIds` 上限 5000；重复直接丢；
4. 事件进**单一 Promise 队列**（串行，不并发抢写同一会话）；
5. 提取文本：array 消息遍历 `text`/`at`，其它类型记 `[type]` 占位；
6. **过滤**：群聊且 `groups=false` → 丢；`allowFrom` 非空且不含发送者 → 丢（日志 `[忽略]`）；
7. **触发判定**：`mode:"all"` 直接放行；`mode:"keyword"` 必须命中关键词（命中后取关键词之后的文本，空则用全文）；
8. **余额闸**：缓存期内复用余额；≤ `floorYuan` → 回一句"余额已到停机线"并 **return（不调模型）**；
9. **选会话**：`bot-session.json` 里的 id；没有则 `POST /x-hub/sessions?cwd=<工作区>` 新建并落盘；
10. **轮换检查**：消息数/存活小时/上下文压力/本段估值任一命中 → `spawnSync(qq-bot-rotate --apply --json --reason …)`；成功切新会话，失败 **fail-open** 继续旧会话；
11. **交接注入**：若 `bot-pending-handoff.json` 存在 → 摘要前缀进 prompt，删除该文件（零额外模型轮次）；
12. **投递 prompt**：
    ```
    [来自 QQ 的对话 · private · 对方 QQ <id>]
    <正文>

    （这是 QQ 对话，请直接给出可以回复给对方的中文回答，不要带内部思考过程。）
    ```
    → `POST /x-hub/sessions/{id}/send {text, mode:"queue"}`；`bot-state.messages += 1`；
13. **等回复**：每 2 秒 `GET /x-hub/sessions/{id}/tail?n=30`，取 `time ≥ startedAt-2000` 的最后一条 assistant 文本；超时 `replyTimeoutMs`（默认 180 s）放弃；
14. **回发**：按 `reply.maxChars`（默认 1200）截断并加"…（回复超长已截断）"，`POST send_private_msg`（群聊则 `send_group_msg`）；
15. **落日志**：`out/bot-bridge.log` 与 stdout，事件链 `[QQ] → [DSH] → [DSH→QQ]`。

## 5. 触发模式

| 模式 | 行为 | 适用 |
|---|---|---|
| `mode:"all"`（生产） | `allowFrom` 白名单内，私聊发什么都直达模型（免前缀） | 自用、单主号 |
| `mode:"keyword"` | 文本需含关键词（`小D`/`ds` 等），取关键词后文本提问 | 群聊/多人场景 |
| `groups:false`（默认） | 群消息一律不处理 | 防刷屏、防误触发 |
| `allowFrom: []` | 空数组 = 不限制（不推荐） | 仅内网测试 |

## 6. 回复处理规则

- 只接受 **assistant** 角色的最后一条新消息（按消息时间 `time` 过滤，避免捞到旧回复）；
- `maxChars` 截断为字符级（中文按 1 字符）；
- 超时/无产出：当前版本**不发送**（只记日志）；配置里的 `reply.noReplyText` 为保留字段，未在此路径使用；
- 消息格式固定为纯文本（不主动带 CQ 码/图片/文件）；NapCat `messagePostFormat:"array"` 下文本是 `[{type:"text",data:{text}}]`。

## 7. 会话轮换（核心成本控制）

### 触发阈值（全部可配）

| 触发 | 配置 | 默认 | 含义 |
|---|---|---|---|
| 消息数 | `rotation.everyMessages` | 120 | 本段处理满 N 条 QQ 消息 |
| 存活时长 | `rotation.everyHours` | 24 | 本段会话创建满 N 小时 |
| 上下文压力 | `rotation.pressureTokens` | 150000 | projcache `contextPressure.pressureTokens` 超 N |
| 本段成本 | `rotation.costYuan` | 2.5 | 本段估算成本 ≥ ¥N |

### `--apply` 一次做 5 件事（零 token）

1. 读 projcache：轮次/步数/token/上下文压力 + 最近 10 轮摘要；
2. 生成交接件 `outDir/<YYYYMMDDHHmm>-<标题>-<id>.md`（实测 1.7–1.8 KB），并把索引行追加到 `rotation.index`；
3. hub 建新会话（`cwd` 默认 `D:\AI\日常`）并改名 `QQ 对话 · 日常 · MMDD-HHmm`；
4. 旧会话改名 `【已轮换 YYYYMMDDHHmm】<旧标题>`，写 `bot-session.json`；
5. 写 `bot-pending-handoff.json`（摘要约 180–200 字 + 交接件路径）→ 桥在下一条 QQ 消息前注入后删除。

> 失败策略：轮换脚本失败只记日志、继续用旧会话（不阻塞聊天）。

## 8. 余额闸

- 每次消息先查余额（`checkSeconds: 300` 内复用缓存）；余额 ≤ `floorYuan`（默认 30）→ 直接回"余额已到停机线…充值后自动恢复"，**不创建模型回合**；
- 端点与 token 均本地读取：`balance.endpoint` + `balance.tokenFile`（默认 `~/.dsh/balance-widget.json`）；
- 与 DSH 的「待机零消耗」一致：桥空闲、余额充足时不产生费用。

## 9. 安全与隐私设计

| 面 | 措施 |
|---|---|
| 谁能触发 | `allowFrom` 白名单（实测只认主号）；群聊默认关闭 |
| 凭据 | OneBot token、hub token、余额 token 都只存本地文件；仓库仅 example |
| 账号隔离 | 小号用独立 QQ 副本；不与主号客户端共用；不做群发/加好友/主动私聊 |
| QQ 数据 | 不读数据库、不解密、不碰进程内存；主链路只走 OneBot 事件 |
| 日志 | 只落本机；不打印完整 token；QQ 内容属私人数据，不自动外传 |
| 合规 | 遵守 QQ/NapCat 条款；账号风险由使用者承担 |

## 10. 可观测性（状态文件与日志）

| 文件/字段 | 作用 |
|---|---|
| `out/bot-bridge.log` | 启动参数、`[QQ]`/`[DSH]`/`[DSH→QQ]`/`[轮换]`/`[交接]`/`[余额闸]`/`[忽略]` |
| `out/bot-session.json` | 当前绑定的 DSH 会话 id（轮换后更新） |

| `…/交接/*.md` + `日常/QQ机器人/README.md` | 每段会话的可读交接件与历史索引 |
| `--check` | OneBot / hub / session 三项自检 JSON |

## 11. 已知边界与限制

- **单用户设计**：一条主号 ↔ 一个小号；不做多用户路由/权限体系；
- **只支持私聊**（当前生产）；群聊要开 `groups` 并自行处理 @/刷屏；
- **NapCat 重启掉登录**：需重新扫码；桥不需要重启；
- **DSH 宿主重启后** hub 端口/token 会变，桥启动时读取 `session-hub.json`，因此**必须重启桥**；
- UI Automation 兜底方案读不到提权（管理员）QQ 窗口；本仓库主链路不依赖它；
- 不处理图片/文件/语音消息内容（只占位）；不代发图片/文件；
- 回复是单条文本，超长按 `maxChars` 截断；
- 交接件只带最近 10 轮摘要，旧细节需回查旧会话或 QQ 记录工具链。

## 12. 实测数据（2026-10-21/22）

- 轮换实测（21:52–21:54）：`session-af4e37fe`（1 轮 ¥0.02）→ `session-a839a284`（交接件 1.7 KB）→ 首条注入 183 字；再触发 → `session-026c6ac0`（交接件 1.8 KB，注入 196 字），两次回复均成功；
- 生产阈值恢复：`everyMessages=120`，桥重启后正常监听；
- 3 个机器人会话共 8 轮：69,189 未命中输入 / 853,632 缓存读 / 10,286 输出 ≈ **¥0.14**（详见 02）；
- 桥空闲：无模型调用、成本 0；余额 ≤¥30 闸门实测会直接回停机提示。
